# 沖煮步驟：每一步存自己的秒數與本次水量

取代 ADR-0002（#155）。

`brew_plans.steps` 的每一步只存**自己的**長度 `seconds`（整數 1–600），注水另存**本次**水量 `water_g`；不再存任何從 0:00 起算的時間（`at_seconds` / `until_seconds`），也不存累計 `to_g`。一步的開始時間是前面各步秒數的加總，總時間是全部加總，累計與總水量也都是加總，全部算出來、不存。

- 注水：`{ type: 'pour', seconds, water_g, bloom?, water_temp?, note? }`；等待：`{ type: 'wait', seconds, note? }`。
- 注水的秒數是它在時間軸上佔的整段：注水本身加上注完後的靜置，到下一步開始為止。靜置時要做的事（輕搖、旋轉、等到滴落約 70%）寫在這一注的 `note`，不另開等待。等待是沒有注水、自己有秒數的步驟，實際上多半是最後的「等待滴完」。
- 每一步至少 1 秒，所以沒有長度 0 的步驟：時間條一步一格、寬度依秒數，#146 的「等待併進前一注那一格」拿掉；之後的計時器依序對每一步倒數 `seconds` 即可。
- 驗證：第一步是注水（「從 0:00 開始」自然成立，不再檢查）；`bloom` 只能在第一注；`water_g` 在 (0, 2000]，全部注水加總也 ≤ 2000，保住原本 `to_g ≤ 2000` 的總量上限。上限照 ADR-0001 只在 Worker。
- `schema_version` 改為 2。正式環境還沒有使用者的計劃（#146 部署當天、作者確認），所以 migration 直接刪掉既有列，不寫 v1 → v2 的轉換；4 個內建手沖法在 `app.js` 手寫成 v2。

ADR-0002 選絕對時間軸，是為了「改一步不會讓後面漂移」與「累計好驗證」。實際編輯時作者要的正好相反：每一列直接調「這一步幾秒、注幾 g」，第一注也有自己的時間；改一步讓後面跟著移，正是想要的行為。絕對時間軸下一注的長度要看下一步，第一注沒有可調的時間，最後一注還得靠一個空的等待才有範圍（4:6 的 3:30、Ultimate 的 1:45）。

## Considered Options

- **注水的秒數只算注水本身**：不採用。靜置沒有地方放，要嘛每注後面都加等待，要嘛再存「下一步何時開始」，等於把絕對時間帶回來。
- **允許 0 秒的步驟**：不採用。v1 轉換最省事，但會留著「注下去馬上進等待」的特例，畫面要合併格、計時器要跳過。
- **時間改存秒數、水量照舊存累計**：不採用（作者：統一）。兩種座標混在同一個步驟裡，編輯頁本來就以本次為輸入。
- **Worker 讀取時把 v1 轉成 v2，或寫 SQL migration 轉換**：不採用。沒有要保留的 v1 資料；Worker 轉換的程式碼要永遠留著，SQL 的 `json_each` 寫不好合併規則。
